Bread of the Wild · 版本管理与命名指南

项目规则｜2026-09-19 用户确认｜适用于整个 GDATtest 工程

本指南规定游戏版本号、开发阶段、Git 分支、提交和标签的命名方式。它是本团队的约定，借用语义化版本的结构；游戏里程碑由团队验收要求决定，不等同于严格 SemVer 的公共 API 兼容性承诺。

版本状态以本地 Git 标签和验收记录为准。 文中的 v0.3.1 等用于解释命名规则，不代表这些版本已经存在。本工程以根级完整仓库管理源码、资产和配置；现已发布至 GitHub 私有仓库 djwcb2333/GDATtest；当前里程碑见根级版本记录.md。操作前仍须核对其他任务的交接与工程写入权。

1. 一分钟速查

对象 本项目规则 示例
正式工程目录 沿用现有目录，不把版本号加到工程路径上 E:/Unreal Project/GDATtest
工程文件 沿用现有名称 GDATtest.uproject
游戏版本号 主版本.次版本.修订版本 0.3.1
预发布版本号 版本号-阶段.阶段内序号 0.4.0-alpha.2
Git 版本标签 在版本号前加小写 v v0.4.0-alpha.2
主分支 main main
功能分支 feature/简短英文描述 feature/enemy-hitbox
修复分支 fix/简短英文描述 fix/menu-input
提交说明 类型: 具体修改内容 fix: 修复敌人受击重复扣血

不要使用“最终版”“最终最终版”“最新可用版”来代替版本号。日期可以出现在交付说明里，不能独自替代版本号与提交记录。

2. 看懂 0.3.2：三个数字分别负责什么

位置 名称 本项目含义 例子
第一位 主版本 Major 大的正式发布阶段 0.x.x 开发中；1.0.0 首个正式交付版本
第二位 次版本 Minor 一批新功能或内容形成了可验收里程碑 0.2.0 → 0.3.0
第三位 修订版本 Patch 对已有版本进行问题修复或小幅调整 0.3.0 → 0.3.1

增加次版本时，修订版本归零，如 0.3.8 → 0.4.0。增加主版本时，其余两位归零，如 1.7.4 → 2.0.0。是否进入新的主版本由团队明确决定，不按提交次数自动升级。

这些数字不是小数：0.9.0 后可以是 0.10.0，0.10.0 比 0.9.0 新。数字前不补零，写 0.3.1，不写 00.03.01。

版本号不表示完成百分比。 0.8.0 不代表游戏做完了 80%；1.0.0 表示达到事先约定的首个正式交付范围，并不意味着以后永远没有问题。

3. Prototype、Alpha、Beta、RC 与正式版

阶段名表示版本的成熟程度。团队应先写清该里程碑包含什么，再判断是否符合下一阶段条件。

阶段 本项目约定 名称示例
Prototype 原型 验证玩法想法，结构和内容仍可能大改 在交付说明中标注“原型阶段”；不强制另造一种标签格式
Alpha 开发测试 核心玩法持续完善，仍会增加或调整功能 0.3.0-alpha.1
Beta 完整范围测试 本次交付约定的功能与内容基本齐全，重点是测试、平衡和修复 0.3.0-beta.1
RC 候选发布 Release Candidate；已接近正式发布，等待最后验收 0.3.0-rc.1
正式版 达到该次版本约定的验收条件，去掉阶段后缀 0.3.0

一个目标里程碑可以这样推进：

0.3.0-alpha.1
→ 0.3.0-alpha.2
→ 0.3.0-beta.1
→ 0.3.0-rc.1
→ 0.3.0

同一阶段的序号从 1 开始，每次实际交付新的预发布快照就递增。进入新阶段后从 1 开始，如 alpha.4 → beta.1。仍在同一个 Alpha 里程碑内修正问题，可以递增为 alpha.2；已经发布不带后缀的 0.3.0 后修复问题，则使用 0.3.1。

开发中的整个游戏也可以发布一个稳定的阶段成果 0.3.0。它的“正式”仅针对该次里程碑，不等于整款游戏已完成。Demo 描述演示的内容范围，不能单凭“Demo”判断它属于 Alpha 还是 Beta。

4. 什么时候提交，什么时候增加版本号

Commit 提交记录一次清楚的修改。Tag 标签给某个确定提交取一个版本名字。多个提交可以共同组成一个对外交接或内部验收版本。

示例：

feat: 增加敌人受击体积
fix: 修复同一次攻击重复扣血
art: 调整受击反馈效果
docs: 补充受击参数教程
          ↓ 完成这批工作的验收
标记版本 v0.4.0-alpha.1

不必每改一个按钮就增加游戏版本号。完成一项清楚的工作可以提交；需要让别人试玩、交接，或需要保留明确里程碑时，再按规则确定版本并创建标签。

已交付的标签固定指向原提交。发现问题时增加下一版本，不把同一个 v0.3.1 标签移动到另一份代码上，也不悄悄用不同文件覆盖同名交付件。

5. 分支怎么命名

分支 用途 示例
main 团队主线，接收已经完成约定检查的工作 main
feature/... 新功能或成组内容开发 feature/dialogue-sequence
fix/... 修复已有行为 fix/enemy-hitbox

描述部分使用简短英文、小写字母，单词之间用连字符，避免空格和“new”“test2”这类难以辨认的名称。一个分支尽量对应一项明确任务。

分支只说明工作方向，不说明版本已经验收。名为 main 的分支也不能替代测试记录。

同一份运行中的 UE 工程仍然只能有一个写入者。 建了多个分支，不意味着多个任务可以同时在同一个磁盘工程目录中保存、编译或切换分支。当前项目继续按写入协调表交接；未来团队各自克隆后，仍须协调同一蓝图或地图的修改。

6. 提交说明怎么写

格式：类型: 具体修改内容。冒号使用英文半角，冒号后留一个空格，内容可以使用中文。

类型 用途 好的示例
feat 增加功能 feat: 增加可复用字幕队列
fix 修复问题 fix: 修复敌人受击重复扣血
art 美术资源与视觉调整 art: 调整村庄地形材质
docs 教程和说明 docs: 补充版本命名指南
refactor 整理实现，预期行为保持一致 refactor: 整理字幕队列推进逻辑
chore 工程维护和版本管理配置 chore: 建立完整工程版本基线

这些是本团队采用的类型，其中 art 是为游戏美术工作约定的类型；不声称它们全部属于某个外部强制标准。

避免只写“更新”“改了”“修复一些东西”。修改较复杂时，在提交描述中补充为什么修改、验证了什么、还有什么未验证。

例如：

Summary：fix: 修复敌人受击重复扣血

Description：
同一次攻击对同一目标只结算一次伤害。
验证：填写本次实际执行过的检查与结果。
未验证：如实填写未进行的独立运行或打包验证。

不要把上面的验证示例当成当前项目已经完成的测试。

7. 版本记录至少写哪些内容

每次标记里程碑时，记录以下信息：

字段 填写方法
版本号 / 标签 如 0.4.0-alpha.1 / v0.4.0-alpha.1
对应提交 记录 Git 中实际存在的提交 ID，不编造编号
日期 使用 YYYY-MM-DD
本次范围 新增、修复或调整的具体功能和资源
环境 实际 UE 版本，以及需要的 C++ 工具和插件
验证 分别列出静态检查、编译、PIE、独立运行、打包结果
已知问题 明确会影响试玩或协作的问题
存档兼容性 是否检查旧存档；不确定时写“未验证”

“能提交 Git”“能完整克隆”“C++ 编译成功”“PIE 正常”和“发行版打包成功”是不同结论，必须分别记录。不要只写一个没有范围的“测试通过”。

8. 游戏版本与存档格式分开记录

游戏版本用于识别某次工程或游戏交付，存档格式版本用于识别数据结构。一次材质调整可以改变游戏交付版本，却不需要改变存档结构。

只有存档结构需要兼容或迁移处理时，才由功能实现者检查并调整工程已有的存档版本机制。本文不新增字段、不修改已有版本值、不自动迁移或删除任何存档。 不能因为改了游戏版本号，就推断旧存档一定兼容。

9. 在 GitHub Desktop 中对应哪里

你要做的事 界面概念
确认正在操作哪份仓库 左上 Current repository，完整工程根目录应为 GDATtest
确认当前工作分支 顶部 Current branch
给一次修改命名 Changes 面板下方的 Summary；补充说明填 Description
本地保存修改记录 Commit … to 分支名
查看已保存记录 History
发布或上传 Publish repository / Push origin；提交后按本次授权推送

Git 标签是版本标记；GitHub Release 可以基于标签提供版本说明和交付附件。它们不需要与每次提交一一对应。本地创建标签不要求先上传 GitHub。

本指南讲命名规则。完整工程首次接入、Git LFS、克隆、C++ 环境和故障处理另见外部交付目录 UE_Whitebox_Delivery/GitVersionControl_20260919/本地版本管理方案与教程.html。建立仓库后，根目录的 README_GDATtest.md 将随工程提供基础使用说明。

10. 这次重建 Git 如何应用本规则

  1. 版本管理接续前，重新读取项目状态和写入协调表，核对之前的工程任务已经结束并释放写入权；此次用户已经发送“继续”并完成交接核对。
  2. 按已授权范围保存旧 Git 元数据，并清除工程内两处旧仓库的嵌套状态；不搬动或重建 UE 资产。
  3. 从 GDATtest 根目录建立完整工程的本地 Git 与 Git LFS，包含两个 C++ 模块、完整 Content、Config、.uproject、本指南和其他必要文件。
  4. 首次提交使用 chore: 建立 Bread of the Wild 完整工程版本基线。
  5. 首个本地完整工程基线使用标签 v0.1.0-alpha.1，须在文件保留、完整克隆和 Desktop 接入检查完成后标记。它表示当前工程可追溯的 Alpha 基线，不自动宣称本任务重新验证了游戏编译、运行或打包。标签是否已创建，以 Git 的实际记录为准。
  6. 本次先完成本地版本管理和 GitHub Desktop 接入。上传、远程仓库和共享权限留待后续决定。

这是历史从当前完整工程重新开始的编号，不代表此前的开发成果被删除。工程目录仍为原 GDATtest。

11. 发布前自查

  • 版本号格式正确，数字没有前导零，阶段名使用小写。
  • 清楚区分了分支、提交、标签和 GitHub Release。
  • 标签对应明确的真实提交，且没有移动已交付标签。
  • 本次新增、修复、验证和已知问题有记录。
  • 存档兼容性有说明，未经验证的部分没有写成已通过。
  • Source、Content、Config 和 .uproject 属于同一套完整工程版本。
  • 工程目录与资产路径保持原样，没有通过复制“最终版文件夹”代替版本管理。
